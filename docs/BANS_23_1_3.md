# Backend bans and unbans — 23.1.3

## Operator workflow

Use the existing admin player page's Ban / Unban actions. All mutation endpoints require the configured admin bearer token; no frontend change is required.

- `POST /api/v1/admin/players/{id}/ban`: JSON `{"reason":"operator reason","minutes":60}`. Omit minutes or use 0 for a permanent ban. `include_device` defaults to true and covers both stored native and Socket.IO device identifiers. False bans the player only.
- `POST /api/v1/admin/players/{id}/unban`: atomically removes the player and both currently stored device bans, including expired duplicate records. Response includes `removed` and `still_banned`.
- `POST /api/v1/admin/bans`: JSON with `kind` (`player`, `device`, `ip`), `subject`, `reason`, `minutes`. Upserts that exact kind/subject, replacing historical duplicates instead of layering a permanent record over a temporary one.
- `DELETE /api/v1/admin/bans?kind=ip&subject=...`: explicitly remove a shared IP ban. Unbanning one player deliberately does not remove a shared IP ban; `still_banned:true` reports the remaining restriction.
- `GET /api/v1/admin/bans`: includes expired records for audit/history. Enforcement checks the deadline at request time, so expiry needs no scheduled job or server restart.

Negative/overflowing durations, unknown kinds and blank subjects return 400 without partial mutations. Player aliases resolve to the canonical account. A complete player/device mutation is persisted atomically before notification. Failed persistence rolls in-memory bans back and does not revoke sessions.

## Stock contracts

The stock HTTP auth callback at RVA `0x3C1483C` handles bans only after successful HTTP/decryption. HTTP 403 therefore does not show its AccountBlockedWindow. The backend now returns encrypted HTTP 200 with `err_code=1402`, the existing `player_id`, echoed `hash`, and integer `create_to` / `wait` fields, without a socket URL/token.

`create_to` is NOT the expiry of the backend ban. The stock AccountBlockedWindow uses it to enable the destructive Start New Game action. It is deliberately set to 2147483647 to keep that reset action disabled; backend expiry remains authoritative. Do not press account-reset actions to test bans or unbans. Ban reasons remain in the operator API; the stock window has its own built-in Terms of Use text.

The existing thin bootstrap's exact User-Agent `opg3d-thin-client/23.1.3` receives only its already-existing identity/session when banned, without rotation, creation, progress access or Photon access. This retains the backend origin until stock HTTP auth can display the native window. This compatibility selector is not permission to use gameplay endpoints; other banned native registration callers still receive 403.

Already-connected sessions are checked before every implemented encrypted gameplay handler. A ban commit is serialized against dispatch and native auth/capability responses: an in-flight command finishes before the successful ban response, and subsequent commands cannot mutate progress. Denials echo `req_id`, with stock revoked authorization code 1419 and numeric reason 1. Store failures during socket identity resolution now fail closed.

Online notification uses the real stock `expired_session` event and numeric `reason=1`, encrypted under the affected session's codec, in the exact Socket.IO namespace retained from auth (the device uses `/sio`). Sending it to the root namespace was silently ignored. Do not send `ban`: that name is the stock outbound anti-cheat report, not the server's revocation event. Notification targets only matching sessions. Full queues trigger only the affected transport's abort; durable checks still apply on reconnect.

No profile, progress revision, currency, XP, inventory, receipt or stored native session is reset by a ban/unban.

## Device verification — 2026-10-20

On the connected rooted Android device with client 23.1.3:

1. Short two-minute test bans were applied to the existing account, then explicitly lifted in a guarded test script's finally block.
2. Stock startup displayed the real AccountBlockedWindow with the built-in ban explanation. Read-only diagnostics confirmed auth state 8 (Paused) and the native banned flag set.
3. The corrected online event was consumed: stock auth changed from 1 (Authorized) to 8 (Paused). The lobby itself remained visible and the native banned flag stayed false until HTTP auth on the next launch. This is not an automatically displayed ban overlay in an already-open lobby.
4. After unban and restart the same account returned to the lobby. Level 65, XP 0, 997417 coins, 997654 gems, revision 26 and all 87 progress slots remained present. These are observed values, not restore defaults. No application data was cleared and no older profile was restored.
5. The final test left zero ban records. Private state/binary backups and detailed diagnostics are outside the repository.

### Boundaries

- To display the native ban window after an online ban, restart the game. After unban/expiry, restart if the stock client is still paused/on the ban screen. This implementation does not alter the frontend to force an AuthorizationScene transition.
- An existing battle in externally hosted Photon is not authoritatively controlled by this HTTP/config backend. New AppID requests are denied while banned, and backend progress writes are denied, but this is not a verified Photon-room kick or protection against a cached AppID. That requires Photon-side authorization/room control.
- Device identifiers are compatibility identities, not hardware attestation. A full anti-cheat/identity redesign is outside this fix.
