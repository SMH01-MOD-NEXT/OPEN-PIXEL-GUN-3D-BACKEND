# Живая популярность карт: исследование и ТЗ для фронтэнда 23.1.3

## Обновление после подключения двух устройств — 2026-10-22

Nothing и Realme подтвердили реальный онлайн-вход в одну Photon-комнату на карте
1001 (режим 2, протокол 16.6.0mm_v2), offlineMode=false; штатные join/leave
передаются. Добавлен консервативный серверный учёт уникальных аккаунтов для
обычной группы 0 по собственному каталогу клиента, явному mmrank=0 и проверенной
платформе/варианту. Старые нулевые ответы ниже описывают состояние **до** проверки.

Новый APK для этого ограниченного пути не нужен. Все рейтинговые/неоднозначные
группы, другие варианты/платформы, авторитетность Photon, межрегиональная
агрегация и гарантированное обнаружение отдельного обрыва Photon при живом API
по-прежнему не решены. Для полного покрытия нужны перечисленные ниже нормализованные
снимки/leave/heartbeat либо доверенный серверный поток Photon.

Точные текущие ограничения и проверки: `MAP_POPULARITY_23_1_3.md`.

## Результат первоначального исследования (исторический)

Исправление формата `get_map_popularity` уже выполнено отдельно. Включать на его
месте недоказанные ненулевые счётчики в рамках этого исследования нельзя.

Штатный `update_player_online` содержит больше информации, чем прежний краткий
лог обработчика: в полном производителе присутствуют `protocol`, `mmrank`,
`group`, а при некоторых настройках — `tier_mm`. Поэтому отсутствие этих полей
в `socket.player_online` НЕ является доказательством отсутствия данных у клиента.

Тем не менее сейчас не подтверждён достаточный для корректной агрегации контракт:

- В доступной выборке 20 сообщений есть полные снимки и частичные обновления.
  Нельзя считать каждое сообщение полным снимком и обнулять пропущенные поля.
- Подтверждённый офлайн-матч отправил `game_mode="110002"`, `map="1035"`,
  `protocol="16.6.0mm_v2"`, `room_name="offline"`. Непустая карта/комната и
  корректный протокол сами по себе НЕ доказывают реальное онлайн-подключение.
  Конкретный sentinel `offline` можно отфильтровать уже на сервере; это полезно,
  но не заменяет проверку всего жизненного цикла и настоящего онлайн-матча.
- `game_mode` — составное число, а не готовый индекс режима из запроса популярности.
  В частности, компонент *10000 получает значение из платформенного enum
  GameConnect, а не из проверенного признака offline/online.
- `tier`, `group`, `mmrank`, `tier_mm` нельзя без проверки объявлять одной и той
  же группой популярности. Клиент строит её разными ветками конфигурации.
- Нет подтверждённого положительного онлайн-прогона с двумя клиентами, сменой
  карты, выходом и потерей связи. ADB в момент исследования устройств не видит.
- У текущего бэкенда нет входящего авторитетного потока статистики Photon.
  Наличие AppID/настройки региона само по себе такого потока не создаёт.

**Вывод:** принципиальная невозможность server-only решения НЕ доказана.
На штатных сообщениях возможен учёт сообщаемого присутствия, но включать его
как проверенную реальную популярность пока преждевременно. Ниже — рекомендуемое
минимальное расширение для однозначного контракта. Это ТЗ, а не уже реализованный
получатель/отправитель. APK, Photon и развёрнутый сервис этим изменением не менялись.

## Что ещё может позволить обойтись без изменения APK

1. Подключить устройство и второй клиент к одному тестовому бэкенду.
2. Снять только разрешённые поля присутствия для реального онлайн-входа,
   смены карты, выхода и обрыва связи. Не писать токены, sid, ключи или профили.
3. Доказать соответствие группы из `MapPopularityController` и `mmrank/tier_mm`
   для обычного и специального режима; проверить изменения конфигурации.
4. Проверить первичный полный снимок после повторной авторизации и периодичность
   обновления во время длинного матча, а не только при смене уровня игрока.
5. Если всё покрывается штатным потоком, реализовать его слияние и агрегацию
   без нового события и без новой APK. Если нет — использовать расширение ниже.

Альтернатива без APK — реальный серверный поток Photon: события/статистика
комнат, доступные для конкретного развёртывания, с доступом к их настройке.
В этом случае нужен отдельный контракт доверенного источника; не следует
предполагать наличие универсального REST API статистики только по AppID.

## Минимальное расширение фронтэнда

### 1. Отправлять полный снимок присутствия

Предлагаемое новое событие существующего авторизованного `/sio` канала:
`opg_map_presence_v1`. Имя и схема ниже — новые, не штатные и пока не поддержаны
бэкендом. Их нельзя просто отправить в существующий generic-ack обработчик и
считать интеграцию завершённой.

Пример входа/обновления (синтетические идентификаторы, не реальные комнаты):

```json
{
  "req_id": 104,
  "schema": 1,
  "seq": 1,
  "state": "joined",
  "room_epoch": "example-join-1",
  "mode": 2,
  "map": "1035",
  "protocol": "16.6.0mm_v2",
  "popularity_group": 0,
  "photon_connected": true,
  "photon_offline": false,
  "region": "eu"
}
```

- `mode` — исходный режим, используемый ключом запроса популярности, НЕ `110002`.
- `protocol` — ровно версия матчмейкинга из запроса популярности, НЕ версия APK.
- `popularity_group` — результат ТОГО ЖЕ правила, которым клиент строит группу
  запроса `get_map_popularity` для этой карты/режима. Не подменять `tier` или
  платформенным полем `group`; особые режимы/смещения также требуют проверки.
- Состояние должно соответствовать фактически принятому входу в комнату.
  Нажатие «В бой», начало подключения и успешная авторизация ещё не означают вход.
- Считывать настоящий PUN `offlineMode` и состояние подключения. При неизвестном
  значении не отправлять `joined`, действовать fail-closed.
- `room_epoch` — новый непрозрачный идентификатор каждого входа, без имени/пароля
  приватной комнаты. Не нужен список других игроков или число ботов.
- `seq` монотонно возрастает в пределах текущей авторизованной socket-сессии.
  После новой авторизации нужен новый полный снимок; очередь старой сессии
  не переотправляется в новую. Не доверять клиентскому времени.
- `player_id`/sid/токен отдельным полем не нужны: владелец определяется сервером
  по уже авторизованной сессии, а не по данным произвольного игрока в payload.
- Идентичность бэкенда и Photon-приложения привязывать серверной конфигурацией,
  не принимать от клиента произвольное имя сервера как полномочие записи.

### 2. Жизненный цикл

- После успешного `OnJoinedRoom`, после оригинального callback: снять состояние
  на Unity main thread и отправить полный снимок только при online + joined.
- Каждые 15 секунд в таком матче: свежий полный снимок с новым `seq`.
- При смене комнаты/карты: новый epoch и полный снимок, не инкрементальный счётчик.
- На `OnLeftRoom`, disconnect, ошибке соединения, включении offlineMode или
  возвращении в лобби: отправить `state="left"` с прежним epoch и новым `seq`.
  Выход идемпотентен; для удаления не должны требоваться устаревшие карта/группа.
- На паузе/уходе в фон: best-effort `left`, остановить heartbeat. На возврате —
  заново проверить реальное состояние и отправить полный снимок. Если продукт
  решит считать фоновые, но реально подключённые клиенты, изменить эту политику
  совместно с сервером, а не поддерживать фиктивное присутствие.
- При закрытии процесса/обрыве связи доставка `left` не гарантируется: TTL сервера
  обязателен. После восстановления socket — авторизация и новый снимок.

Не блокировать callback сетевым ожиданием. Держать ограниченную очередь,
не более одного актуального снимка; сетевую отправку/повторы делать вне main
thread, не обращаться к Unity/IL2CPP объектам из фонового потока. Не менять
успешность подключения, офлайн-флаги, сообщения Photon или логику матча ради
телеметрии. Строки интерфейса, если они понадобятся, только в локализации.

### 3. Точки интеграции в нашей сборке

Проверенные по owned dump 23.1.3 arm64 ориентиры, а не переносимые между версиями
адреса. Предпочтительно разрешение managed-методов существующим resolver:

| Назначение | Метод / RVA |
| --- | --- |
| Снимок штатного присутствия | `丕东一一丝丆专丆丁.上丂丏丑丟东丁丙丛()` — `0x250D038` |
| Полный производитель полей | overload с тремя аргументами — `0x250D52C` |
| Обновление коллектора | `丙丂丘与丝丌一丌业.不丆万丈专丌丒与七` — `0x3927160` |
| Чтение/достройка коллектора | `世东世丄丛丅丝丝丈` — `0x39272F0` |
| Вычисление группы запроса | helper `0x33C42D4`, проверять его конфигурационные ветки |
| Разбор ответа популярности | `MapPopularityController` callback — `0x33C433C` |
| PUN offlineMode getter | `丟丝专丄丑世丞世丒.丑丂丞下世东丆丝不()` — `0x44665E4` |
| PUN offlineMode setter | `丟不业丏七丗丈丌丁(bool)` — `0x446663C` |
| GameConnect вход | `OnJoinedRoom()` — `0x14D7054` |
| GameConnect выход | `OnLeftRoom()` — `0x14D75F0` |
| GameConnect disconnect | `OnDisconnectedFromPhoton()` — `0x14D6E84` |

В `opg3d/src/main/cpp/photon_trace_2313.h` уже есть hooks `ConnectionControl`;
в `photon_2313.h` есть resolver методов PUN. Не устанавливать второй hook на уже
перехваченный метод: подключать наблюдение к существующему wrapper/общему
диспетчеру, сохраняя ровно один вызов оригинала. Существующие диагностические
изменения в `photon_trace_2313.h` не принадлежат этой задаче и сохранены.

Самый маленький патч может добавлять перечисленные поля и полные снимки в
существующий `update_player_online` вместо нового события. Но тогда необходимо
явное поле версии расширения и отдельная серверная ветка: legacy delta нельзя
неявно трактовать как полноценный v1-снимок. Не включать одновременно два
независимых пути, иначе появится двойной учёт.

## Обязательная серверная часть после выбора контракта

1. Отдельный обработчик с проверкой схемы, размеров, чисел, строк и авторизации;
   запрет подмены аккаунта и запись только за собственную сессию. Rate limit.
2. Запись временного присутствия, не прогресса/экономики. Один аккаунт — один
   вклад; новая авторизованная сессия отменяет прежнее владение, старый выход
   не удаляет новый матч. Нужна защита от восстановления старого присутствия.
3. Порядок `seq`, epoch и session generation: запоздалые heartbeat/left не
   воскрешают старую комнату. Повторы идемпотентны.
4. Принимать joined только для online + connected + полной валидной комбинации
   mode/map/protocol/group. На offline/left очищать прежнюю запись сразу.
5. TTL 60 секунд от серверного приёма (при heartbeat 15 секунд), удаление при
   закрытии/отзыве сессии, бане; после рестарта пустой реестр. Engine.IO ping
   сам по себе не продлевает доказательство нахождения в матче.
6. Агрегировать по контексту приложения/бэкенда, протоколу, режиму, группе и
   карте. Регионную политику определить явно: stock запрос региона не содержит;
   по умолчанию суммировать регионы только в пределах своего приложения/бэкенда,
   не притворяться, что выдаётся список доступных комнат конкретного региона.
7. `get_map_popularity`: отвечать только на запрошенные комбинации, объединять
   результаты по списку запрошенных протоколов без повторного учёта аккаунта.
   Сохранить нынешние ограничения запроса, `req_id`, целые значения, `data` и
   отсутствие `err_code` на успехе. Не создавать дополнительный уровень версии.
8. Не публиковать ID игроков, комнат, устройств, токены или списки участников
   в ответе популярности/логах. Считать по одному аккаунту, а не actorCount:
   клиентские боты не увеличивают количество подтверждённых аккаунтов.

Это всё ещё **серверный учёт заявленного клиентом присутствия**, а не защита от
модифицированного клиента: поля connected/offline можно подделать. Для действительно
авторитетного учёта нужны доверенные события Photon/проверка членства в комнате.
Не использовать эту телеметрию как основание для наград или античита.

## Проверка перед включением

- Два разных аккаунта на одной карте: 0 → 1 → 2; выход одного: 2 → 1.
- Переход на другую карту, другой режим/группу/протокол: перенос без двойного учёта.
- Офлайн-матч с ботами и `room_name="offline"`: никаких ненулевых счётчиков.
- Лобби, неуспешный join и начавшееся подключение: ноль.
- Длинный матч: присутствие не исчезает, пока реальные heartbeat поступают.
- Обрыв сети/kill: удаление не позже TTL, даже если Engine.IO ещё не собран reaper.
- Новая сессия, старый heartbeat/left, дубли и смена epoch: старое состояние
  не удаляет и не восстанавливает новое; reconnect начинается полным снимком.
- Поддельный player_id, malformed payload, flood и unauth: отказ без записи.
- Изоляция двух бэкендов/Photon-приложений, рестарт, concurrent update/query,
  race-тесты; прогресс и валюты неизменны.
- Проверить именно экран популярности stock клиента и отсутствие исключения;
  отдельно подтвердить ненулевые значения реальными онлайн-клиентами.

## Состояние этой задачи

Готово исследование и данное ТЗ. Новых счётчиков/телеметрии, обработчика v1,
сборки APK, деплоя или изменения Photon dashboard в этой задаче не выполнено.
Текущий обработчик по-прежнему возвращает корректный `data` с нулями.
